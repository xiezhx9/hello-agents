# 基于 Hello-Agents 的学习计划与实践习题

本文面向具备 Python 基础、能够调用大语言模型 API，希望系统掌握智能体开发的学习者。内容以 Hello-Agents 的章节结构为主线，将“阅读教材”转化为“理解概念、完成实验、记录指标、交付项目”的闭环。

建议每周投入 6～8 小时，持续 8 周。时间有限时，可以优先完成标记为“核心”的任务。

## 一、学习目标

完成计划后，应能够：

1. 解释智能体、工作流、工具调用和多智能体系统的边界。
2. 独立实现 ReAct、Plan-and-Solve、Reflection 三类经典范式。
3. 设计包含模型、工具、记忆、规划器和执行器的最小智能体框架。
4. 根据任务选择短期记忆、长期记忆、RAG 和上下文压缩策略。
5. 使用 MCP 等协议把本地服务封装成可复用工具。
6. 从质量、时延、成本、稳定性和安全性多个维度评估系统。
7. 完成一个可演示、可测量、可复现的智能体应用。

## 三、每周学习闭环

每周按以下节奏推进：

1. **阅读**：记录关键概念、适用场景和限制条件。
2. **复现**：先运行章节示例，确保环境和依赖正确。
3. **改造**：替换任务、模型或工具，验证自己是否真正理解。
4. **评估**：至少记录质量、时延、成功率和失败样例。
5. **复盘**：回答“为什么有效、为什么失败、下一步改什么”。

推荐为每次实验保留以下材料：

```text
experiments/
├── config.yaml        # 模型、提示词、参数和环境
├── cases.jsonl        # 输入、期望结果和标签
├── results.jsonl      # 原始运行结果
├── report.md          # 指标、失败分析和结论
└── run.py             # 可重复执行的入口
```

## 四、分阶段实践习题

### 习题 1：区分智能体与工作流（核心）

判断以下任务更适合确定性工作流、单智能体还是多智能体，并说明理由：

- 在线视频的实时字幕翻译
- 电商退款审批
- 多来源研究报告生成
- 本地文件自动归档

**验收标准：** 每个任务至少从输入不确定性、决策空间、错误成本、时延要求四个角度分析。不能只因为“使用了大模型”就将系统定义为智能体。

### 习题 2：完成 PEAS 建模（核心）

为“网页视频实时翻译助手”编写 PEAS：

- Performance：准确率、字幕稳定性、端到端时延、资源占用。
- Environment：网页播放器、音频流、网络、本地硬件。
- Actuators：字幕覆盖层、术语表更新、重试与降级动作。
- Sensors：音频片段、时间戳、语言检测结果、服务健康状态。

**进阶问题：** 哪些指标相互冲突？系统应如何在准确率和实时性之间取舍？

### 习题 3：大模型参数实验（核心）

固定同一组输入，分别调整 temperature、top-p、最大输出长度和系统提示词。每组运行不少于 10 次，记录：

- 输出一致性
- 格式遵循率
- 平均首字延迟
- 平均生成速度
- 无效或虚构内容比例

**验收标准：** 给出参数变化与结果变化的对应关系，而不是只展示若干输出样例。

### 习题 4：实现 ReAct 工具智能体（核心）

实现一个可以调用计算器、时间查询和本地知识检索工具的 ReAct 智能体，并将每次工具调用记录为结构化事件：

```json
{
  "step": 1,
  "tool": "search_notes",
  "arguments": {"query": "MCP 与 A2A 的区别"},
  "status": "success",
  "latency_ms": 86
}
```

**验收标准：** 工具失败时不会无限重试；达到最大步数后可以安全终止；最终答案能追溯到工具结果。

### 习题 5：实现动态重规划

使用 Plan-and-Solve 完成一个至少包含四个步骤的任务。人为让其中一个工具失败，观察系统能否：

1. 识别原计划已不可执行。
2. 保留仍然有效的中间结果。
3. 生成替代步骤。
4. 在重试预算耗尽时给出可解释的失败结果。

### 习题 6：用 Reflection 改进翻译质量（核心）

准备 20 条包含专有名词、数字、否定表达和口语省略的日语文本，设计“初译—批评—修订”的 Reflection 流程。

比较以下两种方案：

- 直接翻译一次。
- 翻译后由审校角色检查术语、遗漏、数字和语气，再生成修订结果。

**验收标准：** 使用盲评或预先定义的评分规则，证明 Reflection 是否改善质量，同时报告额外时延和计算成本。

### 习题 7：构建最小智能体框架（核心）

设计并实现以下核心接口：

```text
Agent
├── Planner
├── Executor
├── Memory
├── ModelClient
└── ToolRegistry
    └── Tool
```

框架至少支持：

- 统一消息结构。
- 工具注册、参数校验和异常处理。
- 最大执行步数和超时限制。
- 可观察的运行日志。
- 可替换的模型客户端。

**思考题：** 哪些能力应放在框架层，哪些应留给具体业务？

### 习题 8：设计三层字幕记忆

为实时翻译场景设计三层记忆：

1. **滑动窗口**：最近若干秒的原文和译文，用于处理代词与省略。
2. **会话摘要**：当前视频的主题、人物和重要结论。
3. **长期术语表**：人名、产品名、技术词汇及固定译法。

**验收标准：** 给出写入、读取、更新和淘汰策略，并设计错误术语被写入长期记忆后的纠正机制。

### 习题 9：比较上下文压缩策略

对一段持续增长的会话分别使用：

- 固定长度截断
- 滑动窗口
- 递归摘要
- 检索式上下文

比较任务成功率、Token 使用量、事实保留率和时延。找出每种策略最容易丢失的信息类型。

### 习题 10：把本地模型封装为 MCP 工具（核心）

将本地语音识别和机器翻译服务封装为两个工具：

```text
transcribe_audio(audio, language?, timestamps?)
translate_text(text, source_language, target_language, glossary?)
```

工具应返回统一错误结构，并明确区分超时、输入无效、模型不可用和资源不足。

**验收标准：** 工具定义清晰、参数可校验、重复调用行为一致，并能被至少一个 MCP 客户端发现和调用。

### 习题 11：比较多智能体与确定性流水线

为“ASR—翻译—字幕审校”实现两套方案：

- 确定性流水线：组件按固定顺序执行。
- 多智能体方案：识别、翻译、审校角色通过消息协作。

比较两者的质量、端到端时延、故障点、调试难度和资源开销。

**预期结论：** 对强实时链路，确定性流水线通常更可控；智能体更适合放在术语管理、异常恢复、离线审校和质量分析等外围环节。实验结果可以推翻这一预期，但必须有数据支持。

### 习题 12：建立评估套件（核心）

建立不少于 30 个样例的测试集，至少覆盖：

- 正常输入
- 空输入和超长输入
- 工具超时
- 模型返回格式错误
- 多轮上下文冲突
- 提示词注入
- 中日英混合内容

建议记录以下指标：

| 维度 | 指标示例 |
| --- | --- |
| 任务质量 | 任务成功率、准确率、人工评分 |
| ASR | CER、WER、时间戳偏差 |
| 翻译 | COMET/BLEU、术语命中率、人工忠实度与流畅度 |
| 性能 | TTFT、RTF、端到端延迟的 p50/p95/p99 |
| 工具 | 调用成功率、超时率、平均重试次数 |
| 稳定性 | 连续运行时长、崩溃次数、恢复时间 |
| 资源 | CPU、GPU、显存、内存和功耗 |
| 安全 | 注入防御成功率、越权调用次数 |

## 五、毕业项目：本地实时视频翻译助手

可以使用本地 ASR 与 MT 模型（例如 SenseVoice 和 Hy-MT2）完成一个网页视频实时翻译助手。

### 参考架构

```text
网页音频
   │
   ▼
音频捕获与 VAD
   │  20～40 ms 音频帧
   ▼
分段与流式缓冲
   │
   ▼
本地 ASR ──► 原文增量字幕
   │
   ▼
本地 MT ───► 译文增量字幕
   │
   ▼
字幕稳定器 ─► 网页覆盖层
   │
   ├──► 术语/上下文记忆
   └──► 指标与错误日志

外围智能体：术语发现、失败恢复、离线审校、质量报告
```

### 功能要求

- 从网页视频或测试音频中持续读取音频。
- 输出带时间戳的原文和译文字幕。
- 支持用户术语表和语言选择。
- 模型不可用时能展示明确状态并自动恢复。
- 提供暂停、继续、清空上下文和导出字幕功能。
- 保存关键性能指标，支持离线复盘。

### 建议验收指标

使用至少 10 段不同说话人和场景的日语音频，报告：

- ASR 的 CER/WER 与 RTF。
- 翻译的术语命中率和人工评分。
- 首条字幕时间。
- 端到端时延的 p50、p95 和最大值。
- 连续运行 30 分钟的错误次数与资源峰值。
- 工具调用成功率，建议目标不低于 99%。
- 网络中断、服务重启和模型超时后的恢复时间。

不同硬件和模型量化版本差异很大，因此不要预先写死时延目标。先测出本机基线，再以“低于音频时长的处理速度（RTF < 1）”作为具备实时处理能力的最低门槛，并逐步降低端到端延迟。

### 最终交付物

1. 可复现的安装与启动说明。
2. 系统架构图和关键技术选择说明。
3. 一键运行脚本及配置样例。
4. 自动化测试集与原始结果。
5. 包含质量、性能、稳定性和资源占用的评估报告。
6. 3～5 分钟演示视频或动图。
7. 一篇失败案例复盘，说明问题、定位过程和改进结果。

## 六、自测清单

每完成一个阶段，用以下问题自检：

- 我能不用教材解释这个概念吗？
- 我能写出一个最小可运行示例吗？
- 我知道它不适合哪些场景吗？
- 我是否记录了可重复的测试输入与配置？
- 我的结论是否有指标或失败样例支撑？
- 更换模型、工具或数据后，系统是否仍然可维护？

学习智能体最有效的方法不是堆叠更多框架，而是围绕真实任务反复完成“建模—实现—评估—复盘”。当每项功能都有清晰的输入、输出、失败边界和量化指标时，课程知识才真正转化为工程能力。
